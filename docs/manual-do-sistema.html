1. Visão geral e como usar este manual

O sistema é um site em PHP que guarda tudo num banco MySQL e desenha as telas com Bootstrap. Ele cuida da parte acadêmica da UniPHD (alunos, cursos, turmas, matrículas), do financeiro (parcelas, boletos e Pix do Itaú, contas a pagar), do atendimento (WhatsApp com IA, e-mail, avisos) e do portal do aluno.

Leia na ordem na primeira vez. Depois use como consulta: cada parte diz onde fica (pasta e arquivo), o que faz e o que trava ou depende de quê.

Regras de ouro antes de mexer em qualquer coisa

  1. Faça backup do banco e dos arquivos antes de qualquer mudança no servidor.

  2. Nunca edite direto no servidor. Mude no seu computador, teste, e só depois envie o arquivo.

  3. Toda mudança no banco vira um arquivo de migração na pasta sql/ (explicado na parte 4). Nunca crie coluna "na mão" sem registrar.

  4. Nunca abra, copie ou envie a pasta credenciais_itau. Ela tem as chaves do banco.

  5. Mude uma coisa de cada vez e teste. Se der erro, você sabe exatamente o que causou.

3. Como uma página funciona por dentro

Toda tela interna segue o mesmo caminho, do clique até a página pronta. Se você entender esta parte, consegue ler qualquer arquivo do sistema.

O caminho de um clique (exemplo: abrir alunos/form.php?id=5)

  1. O navegador pede a página. O servidor roda o arquivo public/alunos/form.php.

  2. A primeira linha carrega o bootstrap.php: require_once __DIR__ . '/../../includes/bootstrap.php';. Ele:

    1. abre a sessão (a "memória" de quem está logado, guardada num cookie);

    2. conecta no banco (config/database.php, função getDB()), sempre no horário de Brasília;

    3. carrega todos os arquivos de includes/;

    4. se for um envio de formulário (POST), confere o token CSRF. Sem ele, recusa com "Sua sessão estava desatualizada".

  3. A página confere quem é você: exigirLogin() manda para o login se ninguém estiver logado. Ela também derruba a sessão se a mesma conta entrou em outro aparelho, ou se ficou parada mais que o tempo de Configurações (padrão 30 min).

  4. A página confere a permissão: por exemplo exigirPermissaoAcao('ativar_aluno', 'Seu perfil não pode...'). Sem permissão, vai para sem_acesso.php.

  5. Se for um envio (POST), salva: valida os campos, grava no banco, registra na auditoria (registrarAtividade), cria uma mensagem verde ou vermelha (flash) e redireciona (redirect).

  6. Se for só abrir (GET), busca os dados no banco com $pdo->prepare('SELECT ...').

  7. Desenha a tela: define $pageTitle e $activeMenu, inclui layout_header.php (topo e menu), escreve o HTML do meio e inclui layout_footer.php (rodapé e scripts).

Coisas do navegador que travam se esquecidas

  • O JavaScript do Bootstrap carrega no rodapé. Um script no meio da página que usa um modal precisa criá-lo só na hora do clique (bootstrap.Modal.getOrCreateInstance(...)). Se não, dá erro e o botão não faz nada.

  • O csrf.js põe o token sozinho em todo formulário e todo fetch. Se você criar uma página nova sem o layout_footer.php, ponha o token à mão ou todo envio será recusado.

  • Máscaras (CPF, telefone, CEP, dinheiro) vêm do mascaras.js pelo atributo data-mascara="cpf". Ele apaga tudo que não é número, então não pode ficar num campo que mostra asteriscos.

  • Neste sistema não se usa alert() nem confirm(). Use as mensagens flash e o data-confirmar.

  • Arquivos JS e CSS ficam em cache no navegador. Por isso alguns usam assetUrl(...), que acrescenta a data do arquivo ao endereço. Se uma mudança de JS "não pegou", recarregue com Ctrl+Shift+R.

Migrações: como o banco muda sem perder dados

Uma migração é um arquivo .sql com as mudanças (criar tabela, criar coluna, criar permissão). Elas ficam em sql/ com a data no nome e devem rodar na ordem da data, uma vez só.

  1. Faça backup do banco (phpMyAdmin › Exportar, ou o comando mysqldump da parte 12).

  2. Rode a migração: no phpMyAdmin (banco › aba SQL › colar › Executar) ou no terminal do servidor com mysql -u USUARIO -p uniphd < sql/migracao_....sql.

  3. Se aparecer "Duplicate column" ou "already exists", ela já tinha rodado. Não é problema.

  4. Quando criar uma migração nova, atualize também o schema.sql, para que um banco criado do zero já nasça certo.

Código novo que usa uma coluna nova trava a tela se a migração não rodou. O erro típico é "Unknown column" ou "Table doesn't exist". Sempre suba o arquivo e rode a migração juntos.

O que trava o login e a sessão

  • Permissões são lidas só na hora do login. Mudou o perfil de alguém? A pessoa precisa sair e entrar de novo para valer.

  • Um login novo derruba o anterior. A mesma conta em dois aparelhos: o primeiro é desconectado na próxima ação.

  • Tempo parado acima do configurado (padrão 30 min) encerra a sessão.

  • Usuário desativado (ativo = 0) não entra.

  • Muitas senhas erradas bloqueiam por um tempo, por e-mail e por endereço IP.

Coisas que só o administrador faz (não dá para liberar por perfil)

Essas telas começam com exigirAdmin():

  • Configurações: sistema, empresa, e-mail, matrículas, arquivos, auditoria;

  • Cadastros auxiliares: perfis, situações de turma, tipos de graduação, feriados;

  • Contas bancárias inteiras: dados, cobrança, API, webhook, tarifas, conferir boletos, renovar certificado;

  • Outras: liberar matrícula com pendência, informar o saldo do fluxo de caixa, dar desconto acima da alçada.

Detalhes que confundem

  • Alçada de desconto: cada perfil tem um desconto_max (%). Acima disso, só o administrador.

  • Professor vê materiais e videoaulas só das turmas dele. A ligação é o campo "professor" no cadastro do usuário (usuarios.professor_id).

  • Quem cria usuários (sem ser admin) só cria nos perfis liberados em "Perfis que pode gerenciar" (tabela perfil_perfis_gerenciaveis), e nunca administradores.

  • Dar baixa ≠ estornar baixa: são duas permissões separadas (baixar_receber e estornar_receber).

  • CPF completo: permissão ver_cpf_completo. Sem ela, aparece 800.3**.***-**. Cada vez que alguém clica no olhinho, fica registrado na auditoria. Na lista de alunos o CPF fica sempre mascarado.

Como criar uma permissão nova (passo a passo)

  1. Crie uma migração com INSERT INTO permissoes (chave, descricao) VALUES ('minha_chave', 'Texto');. Dê a permissão aos perfis de administrador na mesma migração.

  2. Coloque a chave em estruturaPermissoes(). Se não colocar, ela aparece sozinha numa aba "Outras".

  3. Na página, trave com exigirPermissaoAcao('minha_chave', 'Mensagem');. Para esconder um botão, use <?php if (usuarioTemPermissao('minha_chave')): ?>.

  4. Esconder o botão não basta. A página que recebe a ação também precisa conferir, senão alguém pode chamar o endereço direto.

O caminho de um boleto

  1. A matrícula gera as parcelas (gerarCobrancasMatricula).

  2. Na parcela, "Gerar boleto" envia ao Itaú e grava em cobrancas_bancarias com registrada. O boleto vem com Pix (bolecode).

  3. Toda conversa com o Itaú fica em banco_chamadas (aba Auditoria da conta), com os dados sensíveis mascarados.

  4. O aluno paga. O Itaú pede um token em webhook/itau/token.php e avisa em webhook/itau/boletos.php.

  5. O webhook grava o aviso em webhook_requisicoes e webhook_eventos e dá baixa na parcela no primeiro aviso. A baixa operacional (pago, dinheiro ainda não caiu) ou a efetiva (liquidado) só ficam registradas depois.

  6. A tarifa do banco vai para banco_tarifas e aparece descontada no DRE e no fluxo de caixa.

  7. Se a parcela tem desconto de pontualidade, o sistema reemite o boleto com o valor certo (reemitirBoletosPontualidade).

  8. Protesto automático: só se ligado na aba Cobrança da conta (protesto_ativo, protesto_dias). O pedido vai junto do registro, sem texto de instrução no boleto.

O que trava no financeiro

  • Certificado do Itaú vencido (vale 365 dias): nenhum boleto registra e nenhuma consulta funciona. O sistema avisa o administrador 30 dias antes. Renove em Contas bancárias › API do banco.

  • Webhook fora do ar ou URL errada: o aluno paga e a parcela continua aberta. Confira em Contas bancárias › Webhook (avisos recebidos) e use "Conferir boletos" para acertar.

  • Mudar agência, conta, client_id ou certificado errado trava todos os boletos. Por isso a aba API pede senha.

  • Estornar uma baixa exige a permissão estornar_receber. Baixa que veio do banco não se estorna à mão.

  • Excluir parcela com boleto registrado: o sistema pede a baixa do boleto no banco logo depois de salvar (baixarBoletosCanceladosNoBanco). Se o banco falhar, o erro vai para o log; confira em "Conferir boletos".

  • Saldo informado no fluxo de caixa: tudo antes da data do saldo deixa de contar. Para voltar ao cálculo antigo, use "Remover saldo" (só administrador).

  • Inadimplência (parcela em atraso) pode travar o certificado e a matrícula nova, conforme as opções do curso e de Configurações › Matrículas. O administrador pode liberar em matriculas/liberacoes.php.

Segurança que já existe (e não pode ser removida)

  • CSRF: todo envio precisa do token. Fica em bootstrap.php e assets/js/csrf.js.

  • Consultas com ?: protegem contra invasão pelo banco (SQL injection).

12. Como fazer manutenção com segurança

Antes de tudo: o backup

No terminal do servidor (troque USUARIO pelo usuário do banco; ele pede a senha):

mysqldump -u USUARIO -p --single-transaction --set-gtid-purged=OFF uniphd > backup_uniphd_$(date +%F_%H%M).sql
tar czf backup_storage_$(date +%F).tgz -C /var/www/uniphd storage

O primeiro comando salva o banco; o segundo, os arquivos dos alunos e a chave_app.key. Baixe os dois para fora do servidor. Para voltar um backup do banco: mysql -u USUARIO -p uniphd < backup_....sql. Isso apaga o que foi feito depois do backup, então só faça em último caso.

Mudança no código, passo a passo

  1. Ache o arquivo: o endereço da tela no navegador é o caminho em public/. A regra costuma estar no includes/ de mesmo assunto (partes 2, 6 a 9).

  2. Procure pelo texto que aparece na tela. No VS Code, Ctrl+Shift+F com uma frase da tela ("Situação do aluno atualizada") acha o arquivo na hora.

  3. Mude no seu computador e teste localmente (php -S 127.0.0.1:8000 -t public dentro da pasta do projeto, depois abra http://127.0.0.1:8000).

  4. Confira se o PHP está sem erro de digitação: php -l public/alunos/form.php deve responder "No syntax errors".

  5. Mudou o banco? Crie a migração e atualize o schema.sql (parte 4).

  6. Guarde a versão no git: git add -A e git commit -m "o que mudou". Se algo quebrar, dá para voltar.

  7. Suba para o servidor só os arquivos alterados (o git status lista quais), mantendo as mesmas pastas. Nunca suba config/config.php, storage/ nem credenciais_itau/ do seu computador.

  8. No servidor: rode as migrações novas, abra a tela mudada e confira.

Parte 2 · Mapa das telas

Cada tela do sistema, o arquivo que a monta e onde mudar cada detalhe. O endereço que aparece no navegador é o caminho do arquivo dentro de public/.

Como achar onde qualquer coisa da tela é desenhada

Nem tudo o que aparece numa tela está escrito no arquivo dela. Muitas peças (colunas das listas, o CPF com olhinho, as janelas da parcela) vêm de arquivos em includes/ usados por várias telas. O método abaixo acha qualquer uma em poucos minutos.

  1. Veja o endereço. seusite.com/protocolos/listar.php é o arquivo public/protocolos/listar.php.

  2. Inspecione o detalhe. No Chrome, clique com o botão direito em cima dele (o olhinho, a coluna, o botão) e escolha Inspecionar. Abre o HTML daquele pedaço. Anote:

    1. a classe (class="..."), por exemplo ver-cpf;

    2. algum texto fixo perto, por exemplo o title="Mostrar o CPF completo".

  3. Procure em todo o projeto. No VS Code, Ctrl+Shift+F (no Mac, Cmd+Shift+F) e cole a classe ou o texto. Aparecem todos os arquivos onde ele é escrito.

  4. Se estiver em includes/, é uma peça reaproveitada. Mudar ali muda todas as telas que a usam. Para mudar só uma tela, mude a chamada dentro do arquivo dessa tela (exemplo abaixo).

  5. Se estiver em public/assets/js/, é o comportamento (o que acontece ao clicar), não o desenho.

  6. Se aparecer <?= nomeDaFuncao(...) ?>, o desenho está nessa função. Procure function nomeDaFuncao para achar o arquivo dela.
