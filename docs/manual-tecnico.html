Manual técnico do Harmonize Prime

Como o código está organizado, quais contratos internos existem e onde encostar a mão para cada tipo de mudança. Escrito para quem vai dar manutenção — não para o usuário final.

1. Stack e ambientes

PHP 8 puro, sem framework e sem Composer. MySQL via PDO. No front, Bootstrap 5.3 e Bootstrap Icons pelo CDN, mais CSS e JS próprios em public/assets/. Não há build step: editou o arquivo, recarregou o navegador.

ItemOndeObservação
Credenciais do bancoconfig/config.phpFora do Git (.gitignore). Cada ambiente tem o seu.
Conexão PDOconfig/database.phpSingleton estático, ERRMODE_EXCEPTION, EMULATE_PREPARES=false, fuso -03:00 no MySQL.
BancoDB_NAME em config/config.php33 tabelas, InnoDB, utf8mb4. Estrutura em sql/schema.sql.
Fotos de produtopublic/uploads/produtos/Fora do Git. Precisa entrar no backup à parte.
Docroot: a diferença entre local e servidor

No servidor, o docroot aponta para public/ — as URLs saem como /produtos/listar.php. Localmente você roda a partir da raiz do projeto, então as URLs viram /public/produtos/listar.php. É a origem de praticamente todo bug de link quebrado que apareceu até hoje. A loja já é imune a isso (seção 11); o painel ainda usa caminhos absolutos fixos e por isso só funciona corretamente com docroot em public/.

Subir o ambiente local

# docroot na raiz do projeto (URLs com /public/...)
php -S localhost:3000

# docroot em public/ — igual ao servidor, recomendado
php -S localhost:3000 -t public

2. Ciclo da requisição

Toda página começa com require_once .../includes/bootstrap.php. Esse arquivo é o único ponto de entrada e faz, nesta ordem:

session_set_cookie_params()Cookie httponly, samesite=Lax, secure quando há HTTPS.
session_start()Com use_strict_mode ligado.
header() × 4X-Content-Type-Options, X-Frame-Options, Referrer-Policy e HSTS sob HTTPS.
config/database.phpQue por sua vez carrega config/config.php, define APP_NAME e BASE_PATH.
helpers · auth · estoqueFunções utilitárias, autenticação e movimentação de estoque.
imagens · financeiro · lotesMiniaturas, contas a pagar/receber e controle FIFO.
rate_limitContadores de tentativa de login e recuperação de senha.
Ordem sutil que já causou confusão

database.php faz require config.php na primeira linha, mas config.php chama getDB() no fim — função declarada em database.php logo abaixo do require. Funciona porque o PHP registra as funções de um arquivo na compilação, antes de executar qualquer linha dele. Consequência prática: não dá para incluir config.php isoladamente num script CLI; inclua sempre database.php (ou o bootstrap.php).

3. Anatomia de uma página

Toda tela do painel segue o mesmo esqueleto. Copiar uma tela existente é o caminho mais rápido para criar outra.

<?php
require_once __DIR__ . '/../../includes/bootstrap.php';
exigirLogin();
exigirVendas();                      // permissão da tela

$pdo = getDB();
// ... filtros vindos de $_GET, queries preparadas ...

$pageTitle      = 'Pedidos de venda';   // <title> e H1
$pageBreadcrumb = 'Vendas';             // linha acima do H1
$activeMenu     = 'vendas';             // destaca o item do menu
$pageAction     = '<a href="..." class="btn btn-brand">Incluir</a>';

require __DIR__ . '/../../includes/layout_header.php';
?>

<!-- HTML da tela -->

<?php require __DIR__ . '/../../includes/layout_footer.php'; ?>

As quatro variáveis $page* / $activeMenu são o contrato com o layout_header.php. Todas são opcionais — o header aplica ?? '' em cada uma.

Páginas da loja usam o mesmo padrão, trocando layout_header/footer por loja_header/footer e sem nenhuma chamada exigir*().

5. Camada de dados

Não há ORM nem repositórios: cada página monta seu SQL. As regras não escritas, mas seguidas em todo o projeto:

  • Sempre prepare() + placeholders para qualquer valor vindo do usuário. query() só para SQL 100% estático.
  • Filtros dinâmicos se montam acumulando em $where e $params, nunca concatenando valores.
  • Transações em toda operação que toca mais de uma tabela, com try/catch e rollBack().
  • FOR UPDATE ao ler saldo de produto ou lote antes de alterar — evita corrida entre duas baixas simultâneas.
$where  = '1=1';
$params = [];

if ($busca !== '') {
    $where .= ' AND (p.codigo LIKE ? OR p.descricao LIKE ?)';
    $like = '%' . $busca . '%';
    $params = [$like, $like];
}

$stmt = $pdo->prepare("SELECT * FROM produtos p WHERE {$where} ORDER BY p.descricao");
$stmt->execute($params);
Pegadinha do alias

Quando o $where usa alias (p.codigo), toda query que reaproveita esse $where precisa declarar o mesmo alias — inclusive o SELECT COUNT(*) da paginação. Como o PDO está em ERRMODE_EXCEPTION, esquecer isso derruba a página inteira com erro 500. Foi exatamente o bug da busca de produtos.

7. Padrões recorrentes

Endpoint que serve AJAX e POST comum

Usado em todos os lancar_*, estornar_* e item_*. O mesmo arquivo responde JSON quando chamado por fetch e redireciona com flash quando veio de um form.

$ajax = ehRequisicaoAjax();   // header X-Requested-With

function falhar(bool $ajax, int $id, string $msg): void {
    if ($ajax) responderJson(['sucesso' => false, 'mensagem' => $msg]);
    flash('danger', $msg);
    redirect('/vendas/visualizar.php?id=' . $id);
}

try {
    $pdo->beginTransaction();
    // ... trabalho ...
    $pdo->commit();
    if ($ajax) responderJson(['sucesso' => true]);
    flash('success', 'Feito.');
} catch (Throwable $e) {
    $pdo->rollBack();
    falhar($ajax, $id, 'Erro: ' . $e->getMessage());
}

Filtro de período reutilizável

includes/filtro_periodo.php é um partial com contrato explícito: precisa de $dataInicio e $dataFim (strings Y-m-d ou vazias) no escopo, e tem que estar dentro de um <form method="get">. Ele injeta dois <input type="hidden"> e o JS de public/assets/js/filtro-periodo.js preenche esses campos e chama form.submit() — por isso qualquer outro filtro precisa estar no mesmo form para não se perder.

<form method="get">
    <select name="status" onchange="this.form.submit()">…</select>
    <?php require __DIR__ . '/../../includes/filtro_periodo.php'; ?>
</form>

Use sempre esse componente em qualquer tela nova com data. O DRE ainda usa selects de mês/ano próprios — é o único fora do padrão.

Filtro que lembra o último estado

Telas cujo filtro tem default diferente de “tudo” guardam o estado em sessão, senão o acesso pelo menu (sem querystring) reseta a escolha do usuário. Adotado em contas a pagar, contas a receber e fluxo de caixa:

$_SESSION['filtro_contas_receber'] ??= ['status' => 'pendente', 'data_inicio' => '', 'data_fim' => ''];

if (isset($_GET['status']) || isset($_GET['data_inicio']) || isset($_GET['data_fim'])) {
    $_SESSION['filtro_contas_receber'] = [
        'status'      => $_GET['status']      ?? '',
        'data_inicio' => $_GET['data_inicio'] ?? '',
        'data_fim'    => $_GET['data_fim']    ?? '',
    ];
}
$status = $_SESSION['filtro_contas_receber']['status'];

Detalhe que faz funcionar: o form envia todos os campos juntos, então basta um isset() em qualquer um deles para saber que veio de um submit real, e não de navegação pelo menu.

8. Auth e permissões

A sessão do painel guarda user_id, user_administrador, o array user_permissoes e um token_sessao. exigirLogin() valida os três pontos a cada requisição: sessão existe, token bate com o do banco (sessão única) e não estourou o timeout.

exigirLogin()
Só exige estar logado.
exigirAdmin()
Exige perfil administrador. Usado em Configurações, Usuários e Perfis.
exigirPermissao($chave, $msg)
Base genérica; quem falha vai para /sem_acesso.php.
exigirVendas() etc.
Atalhos por módulo: exigirCompras, exigirEstoque, exigirProdutos, exigirClientes, exigirFornecedores, exigirFormasPagamento, exigirFinanceiro, exigirDRE, exigirRelatorioVendas, exigirLojaPedidos, exigirDashboard.

usuarioTemPermissao() devolve true automaticamente para administradores — perfil admin nunca precisa ter as permissões marcadas na tabela de junção.

Sempre nos dois lugares

Esconder o item no menu (layout_header.php) não protege nada — é só cosmético. A proteção real é a chamada exigir*() no topo do arquivo. Toda tela nova precisa das duas.

9. Domínio: estoque

O modelo central do sistema é o de lançamento reversível: digitar o pedido não movimenta nada; o efeito só acontece no lancar_* e é desfeito no estornar_*. O estado fica gravado nas colunas de data do cabeçalho:

ColunaEmSignifica
estoque_lancado_emvendas, comprasEstoque já movimentado. NULL após estorno.
financeiro_lancado_emvendas, comprasContas já geradas.
preco_lancado_emcomprasPreço de venda já atualizado. Repetível, ao contrário dos outros.

Regras que valem para qualquer código novo

  • Nunca faça UPDATE produtos SET estoque_atual direto. Use registrarMovimentacao(), que grava saldo anterior e posterior em movimentacoes_estoque.
  • Entrada de mercadoria também cria lote (criarLoteEstoque); saída também consome lote (consumirLoteFIFO). Manter os dois em sincronia é responsabilidade de quem chama.
  • O flag de estoque negativo vem de buscarConfiguracoes($pdo)['permite_estoque_negativo'] e é repassado como último argumento. Governa tanto a venda sem saldo quanto o estorno de compra já vendida.

10. Domínio: financeiro

Duas tabelas espelhadas — contas_receber (vendas) e contas_pagar (compras) — com a mesma forma: valor, data_emissao, data_vencimento, status e a data de baixa. A diferença de nome da data de baixa é fonte recorrente de erro:

contas_receber
data_recebimento
contas_pagar
data_pagamento

O que decide se a conta nasce baixada é formas_pagamento.modalidade: avista nasce pago com a data preenchida; aprazo nasce pendente. Contas com venda_id/compra_id nulos são lançamentos avulsos — são só esses que o DRE agrupa por categoria.

Competência × caixa

São dois cortes diferentes da mesma base, e não devem bater:

RelatórioFonteData usada
calcularDREvendas + vendas_itens (CMV pelo custo_unitario congelado no item) + contas avulsasdata_venda / data_emissao
calcularFluxoCaixacontas com status = 'pago'data_recebimento / data_pagamento

O fluxo de caixa calcula o saldo inicial somando tudo que foi baixado antes do início do período, junta entradas e saídas em PHP, ordena por data (desempate por criado_em) e acumula o saldo linha a linha.

11. Loja e o problema do docroot

A loja pode ser servida de três formas, e o código não sabe qual está em uso:

CenárioURL da vitrinePrefixo necessário
Docroot em public//loja/index.php/loja
Domínio próprio em public/loja//index.phpvazio
Docroot na raiz do projeto/public/loja/index.php/public/loja

Por isso nenhuma URL da loja pode ser escrita fixa. Dois helpers resolvem em tempo de execução:

lojaUrl($caminho)
Para links entre páginas da loja. Usa dirname($_SERVER['SCRIPT_NAME']) — como todas as páginas da loja vivem na mesma pasta, o diretório do script atual é a raiz da loja.
publicUrl($caminho)
Para assets e uploads. Compara o caminho em disco do script com o de public/ e subtrai o sufixo comum da URL, achando o prefixo que aponta para public/.
<a href="<?= e(lojaUrl('/carrinho.php')) ?>">Carrinho</a>
<img src="<?= e(publicUrl($foto)) ?>">
redirect(lojaUrl('/index.php'));
Limite conhecido

Se o docroot apontar direto para public/loja/, os assets em public/assets/ ficam fora do docroot e nenhum código resolve isso — precisa de symlink ou alias no servidor. O painel administrativo, por sua vez, ainda usa caminhos fixos (/produtos/...) e não passou por esse tratamento.

12. Uploads e imagens

Dois fluxos de upload: fotos de produto (produtos/form.php, até 10 por produto, 5 MB cada) e logo do sistema (configuracoes/form.php, 2 MB). Ambos seguem o mesmo roteiro de validação, que deve ser copiado em qualquer upload novo:

  1. Checar $_FILES[...]['error'] e o tamanho.
  2. Detectar o MIME real com finfo(FILEINFO_MIME_TYPE) — nunca confiar na extensão enviada.
  3. Aceitar só image/jpeg, image/png, image/webp.
  4. Gerar o nome com bin2hex(random_bytes(16)) e forçar a extensão a partir do MIME detectado. É isso que impede subir um .php disfarçado.
  5. Gravar no banco o caminho relativo (/uploads/produtos/{id}/arquivo.jpg) e, se o INSERT falhar, apagar o arquivo.

As miniaturas são geradas sob demanda por caminhoMiniaturaFoto() — na primeira exibição, com GD, salvas em thumbs/ ao lado do original, preservando transparência e o formato de origem. Apagar a pasta thumbs/ é seguro: regenera sozinha.

13. Banco de dados (schema único)

sql/schema.sql é o único arquivo de inicialização: cria todas as tabelas já na estrutura final, com os dados iniciais (configuração id=1, perfis, permissões, usuário admin, formas de pagamento, tipos e status de pedido). O histórico de migrações (002 a 035) foi consolidado nele e removido.

O arquivo não cria nem apaga banco, porque o nome muda por instalação (DB_NAME em config/config.php):

mysql -u root -e "CREATE DATABASE nome_do_banco CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci"
mysql -u root nome_do_banco < sql/schema.sql

Ao mudar a estrutura: edite schema.sql (instalações novas) e aplique o ALTER TABLE equivalente à mão nos bancos existentes (local e servidor).

14. Receitas de manutenção

Adicionar uma tela nova

  1. Crie a pasta em public/ seguindo a convenção da seção 4.
  2. Copie o esqueleto da seção 3, trocando a chamada exigir*().
  3. Registre no array $menus de includes/layout_header.php: ['Rótulo', '/caminho.php', permissao(), 'chave-activemenu']. Um quinto elemento true abre em nova aba.
  4. Use a mesma 'chave-activemenu' na variável $activeMenu da página.

Criar uma permissão nova

  1. Inserir em permissoes (chave + descricao) no schema.sql e, à mão, nos bancos existentes.
  2. Em includes/auth.php, adicione o par de funções seguindo o padrão:
function usuarioPodeVerX(): bool {
    return usuarioTemPermissao('ver_x');
}
function exigirX(): void {
    exigirPermissao('ver_x', 'Seu perfil não tem acesso a X.');
}
  1. Chame exigirX() na tela e use usuarioPodeVerX() no menu.
  2. A tela de Perfis lista as permissões direto do banco — não precisa mexer nela.

Adicionar um campo em Configurações

  1. Coluna nova em configuracoes no schema.sql + ALTER TABLE configuracoes ADD COLUMN ... nos bancos existentes.
  2. Em configuracoes/form.php, o campo precisa aparecer em três lugares: leitura do $_POST, o UPDATE e o array do execute() — na mesma ordem — e o input no HTML.
  3. Consuma com buscarConfiguracoes($pdo)['sua_coluna'].

Criar um relatório novo

  1. Função de cálculo em includes/financeiro.php (ou include próprio), recebendo $pdo, $dataInicio, $dataFim e devolvendo array — sem HTML dentro.
  2. Página em public/financeiro/ só com filtro, chamada da função e a tabela.
  3. Filtro de data: sempre o filtro_periodo.php (seção 7), nunca inputs de data próprios.
  4. Persistir o período em sessão, como faz o fluxo_caixa.php.

15. Armadilhas e débito técnico
